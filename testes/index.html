    Relatório Completo de Testes de Software: Caixa Branca, Caixa Preta e Cobertura

    Metodologia 1: Testes de Caixa Branca (White-Box Testing)

    Os testes de caixa branca baseiam-se na estrutura interna do código-fonte, examinando caminhos lógicos, decisões condicionais, tratamento de exceções e fluxos de dados internos. Estão implementados principalmente em test_whitebox.py.

    Técnicas Aplicadas:

    1. Cobertura de Ramos e Decisão (Branch Coverage):
    2. No serviço FactCheckService, foram testados isoladamente os fluxos de: ausência de chave de API (self.api_key == ""), resposta HTTP diferente de 200, resposta com lista de checagens vazia, alegação sem avaliações e todos os 4 ramos de classificação textual de agências (falsa, verdadeira, enganosa e não verificável).
    3. Cobertura atingida no módulo: 100%.
    4. Cobertura de Condições Múltiplas (Decision Matrix):
    5. No motor MLEngine, foram exercitadas todas as condições da matriz de decisão de desinformação médica: termos milagrosos, termos exagerados, vacinas associadas a Alzheimer/autismo, megadoses de vitamina C, cloroquina/ivermectina em contexto de cura versus estudo laboratorial, reversão de diabetes e correlação de limão com câncer.
    6. Teste de todos os gatilhos regex de extração de trecho suspeito (extrair_trecho_suspeito).
    7. Cobertura atingida no módulo: 83%.
    8. Mocks Assíncronos e Degradação Graciosa:
    9. No sintetizador ElderlyExplanationSynthesizer, teste com mock de resposta bem-sucedida da Groq LLM (Llama 3.1) e teste com injeção de falha de rede/timeout, comprovando que o sistema degrada graciosamente para a síntese didática estruturada.
    10. Cobertura atingida no módulo: 98%.
    11. Mapeamento de Dicionário MeSH e Recuperação Vetorial:
    12. No serviço PubMedService, teste da função de tradução médica para termos MeSH em inglês e teste da bifurcação em que o banco vetorial local atinge o limiar mínimo de similaridade ($\ge 0.12$), dispensando consulta de rede externa.
    13. Cobertura atingida no módulo: 87%.

    Metodologia 2: Testes de Caixa Preta (Black-Box Testing)

    Os testes de caixa preta tratam o sistema como uma caixa opaca, avaliando as entradas fornecidas e as saídas observadas estritamente em função dos requisitos especificados e contratos de API. Estão implementados em test_blackbox.py.

    Técnicas Aplicadas:

    1. Análise de Valor Limite (Boundary Value Analysis - BVA):
    2. Teste do comprimento mínimo de entrada para consulta em /api/verify:
      • Limite inferior inválido: 0 caracteres (string vazia) -> Rejeição imediata com HTTP 422.
      • Limite inferior inválido: 1 e 4 caracteres -> Rejeição com HTTP 422.
      • Limite exato válido: 5 caracteres ("gripe") -> Aceito com HTTP 200 e resposta processada.
      • Carga ampla de texto: 1000+ caracteres -> Processado com sucesso sem estouro de buffer.
    3. Particionamento de Equivalência (Equivalence Partitioning):
    4. Classe válida 1: Consultas do domínio de Vacinação (ex: "A vacina de COVID altera o DNA?").
    5. Classe válida 2: Consultas do domínio de COVID-19 (ex: "Uso de máscaras reduz a transmissão?").
    6. Classe válida 3: Consultas do domínio de Doenças Crônicas (ex: "Água com limão cura diabetes?").
    7. Classe com caracteres especiais, aspas e pontuações excessivas: Processamento íntegro sem falhas sintáticas.
    8. Verificação Estrita de Contrato e Schema REST:
    9. Validação de que toda resposta de /api/verify contém obrigatoriamente os campos do schema Pydantic: classificacao, probabilidade_desinformacao, tipo, tema, nivel_risco, explicacao, origem, evidencias e latencia_ms.
    10. Garantia de que classificacao pertence exclusivamente ao domínio ["verdadeira", "falsa", "enganosa", "não verificável"].
    11. Garantia de que nivel_risco pertence a ["baixo", "médio", "alto"].
    12. Comportamento de Cache e Latência:
    13. Primeira consulta de uma alegação: Processamento completo e armazenamento em cache SQLite.
    14. Segunda consulta da mesma alegação: Servida instantaneamente com latência inferior a 100ms.
    15. Telemetria e Feedback:
    16. Validação do endpoint /api/metrics retornando total de inferências, latência média e distribuição de temas.
    17. Validação do endpoint /api/feedback com aceitação de payload válido e rejeição com HTTP 422 caso os campos obrigatórios sejam omitidos.

    Como Reproduzir Todos os Testes Localmente

    1. Testes do Backend (Pytest + Cobertura):

    # Executar todos os 46 testes com cobertura e detalhes
py -m pytest medfact/server_ml/tests -v --cov=medfact/server_ml/app --cov-report=term

    2. Testes do Frontend (Jest + React Testing Library):

    # Executar todos os 23 testes do cliente
cd medfact/client
npm test -- --watchAll=false

    3. Build de Produção do Frontend:

    cd medfact/client
npm run build

    4. Telemetria e Monitoramento de Data Drift:

    py mlops/scripts/monitor_drift.py
